# Baton 立项书

> 版本：v0.1（草案）　日期：2026-11-10　状态：待评审

## 1. 一句话定义

Baton 是一个运行在终端里的 **agent 调度管理层**：一个面向用户的管控 agent 负责对话与决策，把任务分派给若干职能 agent 执行；所有 agent 共享一个按需查询的**共识库**，不往上下文里硬塞知识。

Baton 本身**不实现 agent**，复用现成的 CLI agent（pi、claude、codex 等）作为执行体。它只负责「谁来做、何时做、做完向谁汇报、共识从哪查」。

## 2. 背景与参考

- 参考原型是 DeepSeek 发布的 super agent 所体现的模式：一个总控 + 多个专职子 agent + 共享工具层。本立项书基于对该模式的公开理解做变体，未逐条核对其官方实现细节（见 §10 待核对项）。
- 本机已有 Orca（worktree / worker / 终端管理）、pi、Claude Code、Codex 等基础设施，Baton 定位为把它们串起来的「指挥棒」，而不是另起一套运行时。

## 3. 要解决的问题

| 现状痛点 | Baton 的回应 |
|---|---|
| 多 agent 协作靠人手工开多个终端、来回复制结果 | 单一入口，管控 agent 自动分派与汇总 |
| 每个新 agent 都要把「组织常识」重新塞进 prompt，上下文膨胀 | 共识库按需查询，agent 只在需要时调 tool 拿事实 |
| 子 agent 的汇报对象混乱，用户同时面对多个 agent | 树状汇报链：职能 agent 只向上级 agent 汇报，用户只面对根 agent |
| 现有多 agent 框架过重，绑定特定模型/SDK | 只做调度协议与 TUI，agent 实现可替换 |

## 4. 目标与非目标

### 4.1 目标（首版 MVP）

1. **单入口 TUI**：终端启动 `baton`，用户只与根管控 agent 对话。
2. **调度机制**：根 agent 根据用户决策选择职能 agent，下发任务、收取结果、必要时回问用户。
3. **汇报链**：任意 agent 都可以充当下级的管控者；汇报对象是「上级 agent」或「用户」，二者只能选一，且全树只有根节点面向用户。
4. **共识库 tool**：提供统一的查询 tool（或知识 agent），供所有 agent 查询组织级事实（作息、发薪日、命名约定、环境地址等），不预填充到任何 agent 的 context。
5. **可观测**：TUI 能看到当前 agent 树、每个节点的状态（空闲 / 执行中 / 等待上级 / 完成）、关键事件日志。

### 4.2 非目标

- 不实现 agent 本体，不做模型调用封装，不做自己的 tool-use 循环。
- 不做 Web UI、不做服务端、不做多用户。
- 首版不做共识库的自动学习 / 写回；形态（文件 / SQLite / 独立 agent）在技术方案阶段再定。
- 不追求通用 workflow 引擎；调度规则以「够用」为准，不预留可配置 DSL。

## 5. 核心概念

```
用户
 └── 根管控 agent（唯一面向用户）
      ├── 职能 agent A（执行体：pi）
      ├── 职能 agent B（执行体：claude）
      └── 职能 agent C（同时是下级的管控者）
           ├── 职能 agent C1（执行体：codex）
           └── 职能 agent C2
共识库 tool ──── 所有节点可调用，只读
```

| 概念 | 说明 |
|---|---|
| **节点（Node）** | 一个运行中的 agent 实例。属性：角色、执行体类型、上级、下级列表、状态。 |
| **管控角色** | 节点的一种能力而非类型：有下级的节点就是管控者。根节点的上级是用户。 |
| **职能角色** | 领受具体任务并执行的节点，可同时是管控者。 |
| **执行体（Runner）** | 实际跑 agent 的东西：现成 CLI agent 子进程，或 Orca worker。Baton 通过适配器与之通信。 |
| **汇报（Report）** | 下级向上级返回的结构化结果：结论、产物路径、待决问题、下一步建议。 |
| **共识库（Consensus）** | 组织级事实集合，通过 tool 查询，不进入任何节点的初始 context。 |

## 6. 范围与交付物

### 6.1 首版交付

1. `baton` 终端程序：启动根 agent、渲染 agent 树与日志、承接用户输入。
2. 调度协议：节点之间下发任务与汇报的消息格式（最小字段集）。
3. 执行体适配器：至少打通 **一种 CLI agent 子进程** 与 **Orca worker** 两条路。
4. 共识库 tool：统一查询接口 + 一份示例共识数据。
5. 文档：技术方案、协议说明、使用说明。

### 6.2 后续可选（不在首版承诺）

- 共识库写回与版本化
- 节点持久化与会话恢复
- 节点间直接通信（当前只允许沿汇报链上下）

## 7. 关键设计约束（立项即定）

1. **用户只面对一个 agent。** 任何下级节点要问用户，必须沿汇报链上抛到根节点，由根节点转述并发起询问。
2. **共识不进 context。** 共识库只通过 tool 查询；禁止在启动时把共识全文注入 system prompt。
3. **调度层与执行体解耦。** 换一个 CLI agent 不需要改调度逻辑，只加适配器。
4. **保持小。** 首版代码量目标控制在「一个人两周能读完」；拒绝为未来场景预留抽象。
5. **本地优先。** 全部运行在本机终端，不依赖远程服务。

## 8. 待决事项（技术方案阶段解决）

| 事项 | 候选 | 备注 |
|---|---|---|
| 实现语言 / TUI 栈 | TypeScript + Ink、Go + Bubble Tea、Python + Textual | 评估标准：与 pi / Claude Code 生态的互操作成本、TUI 成熟度、分发便利 |
| 共识库形态 | 结构化文件 + 检索 tool、SQLite + FTS、独立知识 agent | 评估标准：查询延迟、是否需要推理整合、维护成本 |
| 执行体通信协议 | stdin/stdout JSON、ACP、Orca CLI | 需实测各 CLI agent 的非交互模式能力 |
| 节点状态机 | 待定 | 至少区分：idle / running / waiting-upstream / waiting-user / done / failed |
| TUI 布局 | 重新设计 | 参考图仅表达「树 + 状态 + 日志」三要素，不照搬 |

## 9. 里程碑（粗估）

| 阶段 | 产出 | 验收 |
|---|---|---|
| M0 立项 | 本文档评审通过 | 目标、非目标、约束无异议 |
| M1 技术方案 | 语言栈、协议、共识库形态定稿 | 每个待决事项有结论与理由 |
| M2 骨架 | TUI 能启动根 agent 并对话；一个职能 agent 可被分派并汇报 | 端到端跑通「用户 → 根 → 职能 → 根 → 用户」 |
| M3 共识库 | 共识 tool 接入所有节点 | 新建节点不带任何共识 prompt，能通过 tool 答出示例事实 |
| M4 多级 | 职能节点可作为管控者带下级；Orca worker 适配器 | 三层树跑通，下级提问正确上抛到根 |
| M5 收口 | 文档、示例、已知问题清单 | 他人按文档可从零跑起 |

## 10. 风险与待核对项

| 风险 | 影响 | 应对 |
|---|---|---|
| 各 CLI agent 的非交互 / 编程接口能力不一 | 适配器复杂度失控 | M1 先实测 pi、claude、codex 的 headless 模式，只承诺已验证的 |
| 多级汇报链拉长延迟，用户体感差 | 可用性 | TUI 实时展示节点状态与中间事件，避免「黑盒等待」 |
| 共识库查询变成另一种 context 膨胀 | 违背设计初衷 | tool 返回限定粒度（按 key / 主题），不支持「全部给我」 |
| DeepSeek super agent 的具体机制未核实 | 参考偏差 | 本文只借其模式，不绑定其实现；立项评审前补一次资料核对 |

## 11. 评审需要拍板的点

1. 项目名 `Baton` 是否确认。
2. §4.2 非目标是否有遗漏或过严。
3. §7 五条约束是否全部接受为硬约束。
4. 里程碑是否接受「先单层跑通再做多级」的顺序。
